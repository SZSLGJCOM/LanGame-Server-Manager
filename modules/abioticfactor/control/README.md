# Native current-world save

The current adapter waits for the exact newly-created `USaveCurrentWorld` action, rather than treating `Activate` returning as completion. Matching build/PDB evidence places the action's `bSaveSuccess` at `0x70` and its completion ticker handle at `0x60`; both are zero in its native constructor. `FWorldSaveThread` completes its work before calling that action's `SaveThreadComplete` (RVA `0x40a2fc0`), which writes its own result and schedules its own ticker. Waiting is bounded to 30 seconds, tied to the same world/save identity and never retries. A failed action is a failed operation; missing completion or a replaced world stays unknown.

This still cannot confirm a successful disk write in the standard save mode: `RunStandardSave` (`0x40a1ae0`) calls `UAbioticSaveStatics::SaveWorldData` (`0x40a3630`) and `SavePlayerData` (`0x40a2cc0`), but both ignore `UGameplayStatics::SaveDataToSlot`'s bool result (`0x30a9e70`). Thus native `bSaveSuccess=true` only proves this action reached its completion after serialization and attempted writes. The host rejects `write_confirmed=true` for this adapter. A current request whose own action completes without error now returns `save_completion=requested` and `write_confirmation_pending=false`: the request was processed, while storage completion is not verified. Global queue idle, another action, neighboring autosave output and file timestamps never upgrade it to confirmed. The waiting-world/no-client guard remains intact and no production `StartMatch` or readiness override is introduced.

Starting the instance automatically installs and configures UE4SS `3.0.1-1125-g527a483b`, its genuine upstream `version.dll` proxy and the owned `LgsmWorldSave` Lua mod in the instance's private runtime before creating the game process. The loader is downloaded from its fixed official archive and verified; the correctly generated proxy is bundled with LanGame, so users need no native build tools. Allowed loader SHA-256: `91d5444f41d19d0bb502f0fbdc15d76421e20359e898caa39e41e134c8f87958`. Engine detection remains enabled. The default `dwmapi.dll` did not load in the private-server trial; the official version proxy did load the production bridge. The production bridge has now passed a native invocation trial in a task-owned fresh world, followed by restart readback; details and the completion limit are below.

Preparation bundles this policy with `apps/desktop/src-tauri/src/live_players/unreal_save_protocol.lua`; copying the policy alone does not install a working mod. Loader and mod publications have separate ownership records. The mod owns only its `Scripts/main.lua`, `enabled.txt`, manifest and `langame_world_save` exchange. Loader configuration merges the required native-save settings while preserving other fields, comments and existing Mods; ambiguous entries, unknown core/proxy files and externally edited owned files are preserved and reported as conflicts. A compatible verified loader can be reused. Partial owned publication can resume. A game or loader hash mismatch blocks preparation and saving. Startup handles both first installation and subsequent owned payload refresh. Preparation detaches a shared program into an Independent directory and retains its program lifecycle guard through the actual worker. Shared program files are never modified.

Evidence comes from Steam build **24343458** and its matching shipped PDB, read with the local Microsoft DIA SDK on 2026-10-19. Shipping executable SHA-256: `2563f8d798c8277400acd28eefde604c0ac7d77601627296211af48b30dba25f`.

| PDB `USaveQueueSubsystem`, size `0x88` | Queue count `0x48`, in-flight byte `0x50`; outer is the current world |
| PDB `UAbioticGameInstance` | Native saving byte `0x2e0`; reflected `ActiveWorldSaveName` identifies the current world save |

The bridge verifies one authoritative begun-play world, its owning Abiotic game instance and world-owned queue subsystem. It rejects native saving, any queued work and in-flight save work before invocation. The fixed-build bytes are read only through UE4SS custom properties; PE timestamp, image size and native code windows are checked first, and the host pins/hashes the complete image and loader throughout the exchange. The factory is called once, then its returned async action is activated once, with a fresh current-world/deadline check between them. It does not request a backup or server exit, flush an otherwise empty queue, or mutate player moderation.

Startup also publishes a fresh namespaced session token inherited only by the new managed launch. Lua reads the environment token once at initialization; the host compares every receipt with its current owned session. The current exact-path Shipping process must be the managed primary or a unique direct child of the current bootstrap generation; the host rechecks both identities and uniqueness during the exchange. Requests are tied to that launch token, UUID, boot identity and current-world token; changed world/name, signature drift, timeout and exceptions never cause automatic resend. Native calls run on EngineTick. The actual blocking worker owns the instance mutation reservation and storage lease through completion even if its caller is cancelled.

The current protocol observes this action's own completion before answering. A correlated `ready/invoked/call_returned=true`, `write_confirmed=false`, error-free save receipt returns `save_completion=requested`; it does not claim a complete disk result. Missing completion, native failure, stale request/launch/world identity, preflight rejection and timeouts remain errors and are never retried. Other games that require write confirmation retain their existing completion rules. A neighboring autosave log cannot upgrade the result. Trusted mlua fixtures execute the exact bundled source and cover the factory/activation boundary, action completion, unknown results, replay, world replacement and timeout races. Host classification tests cover the Abiotic-only requested result and reject miscorrelated receipts. This semantic correction has not itself been revalidated by starting a server.

On 2026-10-19 a task-owned ordinary copy of build 24343458 was started after excluding all original `Saved`, Steam cache/config/log directories and application ownership metadata. It used a new world, random private password, fresh process-only launch token and private application-data/temp directories. The game and LAN discovery listeners bound to `127.0.0.1:54180` and `127.0.0.1:14001`; the Steam query listener bound to `0.0.0.0:54181`. The server reached the Facility map, but its loaded modules contained neither the staged `dwmapi.dll` nor UE4SS and no UE4SS log or protocol receipt appeared. The copied process was reclaimed after 53 seconds and **no save request was published**. No existing instance or user save was touched.

The current executable imports `VERSION.dll` but not `DWMAPI.dll`. The fixed upstream [proxy build configuration](https://github.com/UE4SS-RE/RE-UE4SS/blob/527a483b63b4dd0104fe1ca1a3934a06b87fcfb2/UE4SS/proxy_generator/proxy/CMakeLists.txt) supports `UE4SS_PROXY_PATH=C:\Windows\System32\version.dll` and generates the corresponding export table/assembly; its [loader generator](https://github.com/UE4SS-RE/RE-UE4SS/blob/527a483b63b4dd0104fe1ca1a3934a06b87fcfb2/UE4SS/proxy_generator/main.cpp) loads the real system library before `ue4ss/UE4SS.dll`. The repository's existing `scripts/build_dragonwilds_player_query.ps1` was reused with a task-owned output directory to build that ordinary proxy. Its 32 fixed source files passed SHA-256/Git-blob checks, the local system version library passed signature verification, and both CMake phases exited zero. The tested proxy was 448512 bytes, SHA-256 `60c95a24f43760c778847d4b68927c6ed325b109368f7ea9e69f1821228a583c`; upstream/fmt licenses and source/build evidence were retained. Only `version.dll` was staged alongside the same fixed UE4SS DLL; the builder's separate Dragonwilds control DLL was not installed.

A second, separate fresh program copy then loaded that proxy through normal process startup, without an injector. UE4SS automatically detected Unreal 5.4, started the unchanged bundled production `LgsmWorldSave` source and installed its EngineTick prehook. The game remained at `WaitingToStart` with no players; launch-token-matching read-only probes consistently returned `world_unavailable`. The bridge's world/context/begun-play readiness conditions were therefore not established; absence of players alone does not identify which guard rejected the probe. The process was reclaimed after 76 seconds, with no save request published and no retry or readiness override. This verifies normal loader/mod startup and authenticated protocol responses, while the exact readiness prerequisite still needs observation in a genuinely ready world. This first empty-world attempt did not establish native invocation or write completion; the subsequent ready-world trial below resolved invocation and readback. Automatic preparation now supplies the correctly generated version proxy; renaming the DWM proxy is insufficient because its exports are DWM functions.

A subsequent 2026-10-19 trial identified the exact empty-server gate with a separate read-only diagnostic: the unique Facility world had its authoritative GameNetDriver, game state, game mode, owning game instance and world-owned SaveQueueSubsystem, but `MatchState=WaitingToStart` and `bReplicatedHasBegunPlay=false`. This fresh world contained no imported user data and had only its generated Admin.ini. The test setup invoked the engine's zero-parameter native `GameMode.StartMatch` **once**, solely inside that disposable fixture; the state became `InProgress` and begun-play became true. This setup call is absent from the production policy, which keeps its original readiness checks and does not start a waiting user's world.

The unchanged bundled production save policy and protocol then returned `saveprobe.ready=true`. Exactly one authenticated save request returned `invoked=true`, `call_returned=true`, `write_confirmed=false`, with no protocol error. The fresh world produced a valid GVAS `WorldSave_Facility.sav` (344215 bytes) and metadata save (1853 bytes). The process was reclaimed; a separate launch of the same private world loaded an `Abiotic_WorldSave_C` whose reflected `LevelGUID` exactly matched the GUID serialized in that Facility save, reached the same native ready state and answered read-only probes. **No second save request was sent during readback.** Both trials ended with zero task-owned processes remaining. This establishes real native invocation and native persisted-world reload in the fixture, while neighboring native autosave activity is deliberately not assigned causally to the request. Per-request durable completion remains unconfirmed. The response at that historical stage required `write_confirmation_pending=true`; the current host reports a correlated completed action as requested, as documented above, without treating this older trial as a new acceptance run.

On 2026-10-20 the dedicated no-client acceptance exercised ordinary production startup, automatic loader/mod preparation and the same declared `save_world` backend used by Maintenance and server cards in two isolated lifecycle cycles. It made no `StartMatch` call or readiness override. Both the initial run and a fresh managed restart reached declared server readiness, then returned a fresh `saveprobe` receipt bound to the current launch token with `error=world_unavailable`, `ready=false`, `invoked=false`, `call_returned=false` and `write_confirmed=false`. The formal adapter stopped before publishing a save request. Both normal stops recorded native exit code 0 and `crash_flag=false`; independent checks confirmed the two observed Shipping PIDs, fixture directory and all sampled listeners were reclaimed. This passes the no-client protection chain with **zero save receipts**, while actual player-client persistence remains unverified.

After the action-completion protocol update, the same no-client acceptance was repeated on 2026-10-20 with the rebuilt production backend: two launch-bound preflight rejections before native invocation, zero formal save receipts, native readiness after a fresh restart, and two normal native exits with code 0. Independent process and endpoint checks again confirmed that both Shipping PIDs and the disposable fixture were reclaimed. This verifies the updated protection chain; it does not exercise a ready-world save or player-client persistence.
