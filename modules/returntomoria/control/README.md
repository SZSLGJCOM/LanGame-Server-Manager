# Native current-world save

The current manual-save adapter uses fixed build 21872765's `UMorSaveGameManager::AutoSaveSynchronous` (RVA `0x25512a0`) once. Its bool comes from `SaveWorldStateToFile` (`0x256f880`), through native world-file creation, `SaveGameToSlot` (`0x256f2a0`) and `CompleteSaveGame` (`0x2552b70`). A true return confirms this request only when the same manager is idle (`State` at `0x60` equals zero), `NumCharacterProfilesBeingSynced` at `0x74` equals zero, and `LastError` at `0x64` equals zero. Native false is a failed save. Remaining profile synchronization stays unconfirmed. The native adapter validates the full image and loader hashes, fixed code bytes, exact current-world/instance/manager ownership, readiness, and process generation. This completion path replaces the earlier void invocation whose historical acceptance is retained below. Its production local acceptance is recorded below.

The bundled `native/LgsmMoriaSaveControl.dll` is installed automatically. Existing owned two-file Lua installations acquire only this added DLL during stopped startup, with compare-and-swap checks retaining their existing script/enabled-file identities. External edits or an unowned conflicting DLL are preserved and rejected. Trusted policy fixtures cover confirmed completion, explicit failure, unknown delivery, world replacement and no replay; native policy tests reject unfinished manager/profile/error states. Fixtures do not substitute for a live native save.

The new completion path passed a local production acceptance on 2026-10-20 using immutable test image SHA-256 `6875c84c7cd023733a7513b809138a2e347b60be2592052652d3646af9c1885e`. The harness required request-correlated completion and performed two complete cycles on one fresh private world. Both formal save actions returned `save_completion=confirmed` and `write_confirmation_pending=false`; their inner native receipts also reported `status=confirmed` with the corresponding Shipping PID/creation identity. Both immediately following normal stops observed native exit and the product's targeted console-read cancellation, then verified whole-tree exit with native code 0 and no crash. The managed restart used a new run and process generation and reached native readiness. The runner exited 0; independent checks found the test and both pairs of game processes gone, the fixture removed, sampled TCP/UDP ports clear and the source executable hash unchanged. No external cancellation probe, forced-stop substitute, extra input or save-to-stop delay was used. This proves the native API's own request-bound completion and lifecycle, while independent attribution of file bytes and real-player content readback remain unclaimed.

Starting the instance automatically installs and configures the fixed official UE4SS `3.0.1-1125-g527a483b`, its genuine `dwmapi.dll` proxy and the owned `LgsmWorldSave` Lua mod in this instance's private runtime before creating the game process. The archive and installed files are hash-verified; the allowlisted loader SHA-256 is `91d5444f41d19d0bb502f0fbdc15d76421e20359e898caa39e41e134c8f87958`. Engine version detection remains enabled. A fresh private Moria server exercised this loader/profile and the native call on 2026-10-19.

Normal shutdown uses the publisher's native console `exit` command, which saves the current game and stops the server. The `moria_console` transport accepts only this command for this module, checks the unique exact Shipping image and creation identity inside the tracked launch Job, verifies all attached console members, and writes once into an empty native prompt. Console attachment occurs only in a bounded private sender process; the manager never detaches or attaches its own console. Before transferring any game-Job query handle, the parent places the sender in a separate non-inheritable kill-on-close Job held only by the parent. Manager loss therefore also reclaims a stuck sender and releases its game-Job reference, preserving game reclamation on owner loss. The parent retains the process handles and Job, transfers only Job-query rights to that exact sender, and checks process identity before authorization and after its nonce-bound private reply. The sender independently pins the identities and checks their Job membership before the single input write. An incomplete or unknown delivery is not replayed and has no Ctrl+C fallback; timeout cleanup terminates only the owned sender. The module's post-command wait, final grace and complete owned-process-tree exit check remain in force; input delivery alone does not confirm shutdown. The private helper's later native handoff and budget change are detailed below. A no-manual-save production control reproduced the former Ctrl+C shutdown timeout with both bootstrap and Shipping still alive, so manual save was not required to trigger that failure. The first in-process `exit` sender then failed before any input write with AttachConsole error 5; Windows documents that error for an already-attached caller, which motivates isolating the sender. This shutdown path is separate from the manual-save action below.

Private sender replies require exactly one complete line-bound frame with the current nonce and root/Shipping identities. Both worker outcome paths explicitly start a new line: a real libtest child otherwise prefixes its test name on the same line and makes the strict reply unavailable. The identified zero-Job rejection regression reproduced that framing failure before the two newline changes and passed afterward without loosening parsing or sending game input. The related real-child checks also preserve the manager's console, drain delayed/finished replies, reclaim a timed-out sender, and reclaim both a sender holding a transferred game-Job query handle and its inert game fixture when their synthetic manager is terminated. These tests establish sender protocol and ownership behavior; they do not establish native game exit, manual-save durability or content readback.

The complete local lifecycle test on 2026-10-19 reached native readiness, returned one pending formal save receipt and delivered the fixed `exit` successfully. Native logs entered `PrepareToLeaveGame` and `HandlePlayerLeavingGame`, but the complete process tree exceeded the unchanged 27-second shutdown budget. A separate diagnostic used a fresh native copy and new world, bypassed automatic loader preparation and made no manual-save call. It also delivered `exit` once; no UE4SS files or loaded UE4SS module were present. Its bootstrap, Shipping and console processes remained alive through 27 seconds plus a further 120 seconds of read-only observation. Owned cleanup and independent OS checks then confirmed their removal. This excludes UE4SS or manual saving as necessary triggers for that observed timeout; it does not distinguish a native shutdown defect from other managed-launch conditions. That investigation introduced no shutdown retry or production timeout increase. At that stage, complete normal stop/restart, causal disk completion and content readback remained unverified for this build; the later shutdown repair and current acceptance are recorded below.

Follow-up native thread captures on 2026-10-20 established the actual blocking operation: the game main thread had reached `FEngineLoop::Exit` and waited inside Windows `FreeConsole` / `NtClose` from `FMorDedicatedServerInstance::Deinitialize` at RVA `0x22d26c5`; the uniquely named native console input thread concurrently blocked in `ReadConsoleW` at RVA `0x22f5415`. Two captures showed the same main stack and unchanged CPU time. Bounded diagnostic suspension totaled less than one second and cannot explain the earlier 147-second control. The matching native `ReadConsoleW` failure branch logs an error and exits its input loop; it does not resend or execute a command.

The shutdown sender now pins this exact executable's full SHA-256, loaded PE timestamp/size and three native code windows before reading the fixed-build engine exit state. It requires `GIsRequestingExit` (RVA `0x79891ad`) false before writing `exit`, then waits for the native false-to-true transition with `GIsCriticalError` still false. Only after that observed transition can it request `CancelSynchronousIo` once on the unique, exactly named `MorDedicatedServerConsole::InputThread`. It checks the retained process identity and Job membership, thread owner, creation time and name; query-only thread enumeration acquires cancellation rights only for the selected input thread. No memory is written and no thread is terminated. An unsupported or changed image, ambiguous thread or expired deadline fails closed without replaying `exit`. `ERROR_NOT_FOUND` is reported as no pending read, not successful cancellation. Both a cancellation request and a missing pending read still require the supervisor's complete owned-tree exit proof.

The private helper's total deadline is now 12 seconds to include image verification and the native exit-state handoff; its parent sends the bounded remaining budget and retains the absolute deadline. Hash chunks, state polling and thread discovery share that deadline. This replaces the former 5-second queue-only helper budget; the module's 12-second post-command wait and 15-second final grace are unchanged. A second raw native/no-loader/no-manual-save control observed the exit-state transition, requested this one targeted input-read cancellation and independently verified natural whole-tree exit 4184 ms after the one queued `exit`, within the original control's 27-second budget. That diagnostic's native harness and cleanup passed.

The subsequent production acceptance used an immutable test image built from the repaired sender, without any external cancellation watcher, extra console input or thread suspension. Both fresh managed runs reached native readiness, returned one formal save receipt each, observed native engine exit and requested the targeted input-read cancellation. Both normal Stop API calls verified the complete owned process tree had exited and recorded native exit code 0 with no crash. The same private instance restarted successfully between cycles; the harness and runner exited 0 and fixture cleanup passed. Independent OS checks found no remaining fixture processes or listeners on the default and sampled ports. The native void save receipts in that earlier acceptance reported `write_confirmation_pending=true`: those two lifecycle cycles establish normal shutdown/restart behavior, not causal completion of the manual save or real-player content readback.

Microsoft documents that [CancelSynchronousIo](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelsynchronousio) marks an I/O request and does not wait for its completion, which is why API success alone is not a shutdown result.

Preparation bundles this game's policy with `apps/desktop/src-tauri/src/live_players/unreal_save_protocol.lua`; the policy file alone is not an installable mod. Loader and mod publications have separate ownership records. The mod owns `Scripts/main.lua`, `enabled.txt`, its bundled native DLL, the ownership manifest and `langame_world_save`. Required loader settings are merged while preserving other fields, comments and existing Mods. Ambiguous entries, unknown core/proxy files and externally edited owned files are preserved and reported as conflicts; a verified compatible loader can be reused. A partial owned publication can be resumed. Startup handles first installation and subsequent compare-and-swap refresh. A game or loader hash mismatch blocks preparation and saving. Preparation detaches a shared program into an Independent directory; a shared library runtime is never modified. The preparation worker retains the program lifecycle guard as well as the instance/storage reservations.

The bridge selects the unique authoritative `GameNetDriver` world, requires begun play, binds its owning game instance and manager/current world state, verifies the reflected function signature, and reads the fixed-build readiness bytes through UE4SS custom properties. Those custom properties are read only. A disabled native world autosave or restore/busy state is rejected; the bridge does not override the game's policy. PE timestamp, image size and two native code byte windows are checked before those reads; the host also pins and hashes the complete executable and loader.

Each mutation uses a fresh UUID, probe boot identity and world token. Every managed startup publishes a fresh namespaced session token and passes it through the new process environment. Lua freezes that environment token at initialization and echoes it; the host checks its current owned session. A unique exact-path Shipping process must be the current managed primary or its direct child with creation time at least the bootstrap creation time; identities and uniqueness are rechecked during the exchange. An old process cannot inherit the next launch token. The sole call runs on EngineTick. Timeout, exception, caller cancellation and a changed world never trigger automatic resend. The actual blocking host worker retains both the instance mutation reservation and storage-context lease until it ends. The earlier adapter returned a void call and reported `write_confirmation_pending=true`, proving invocation without acceptance or disk-completion evidence. The current synchronous completion gate above replaces that invocation path. No neighboring autosave log or file timestamp is treated as this request's completion.
