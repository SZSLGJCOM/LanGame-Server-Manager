# HumanitZ native player responses

`normal.txt` and `empty.txt` are synthetic info examples. `native-one-player.json` and `native-players.json` preserve the info and Players response structures observed from dedicated-server build 26335264 on 2026-10-31, with synthetic server/player names and account identities. JSON escapes preserve CRLF separators and the absence of a final newline without relying on checkout line endings. No credentials or real player data are included.

The maintained HumanitZ client documents the `info` response header, the `N connected.` count, and the following `Players:` section with one display name per line:

- <https://github.com/Minidoracat/humanitz-bot/blob/main/src/humanitz_bot/services/rcon_service.py>
- <https://github.com/Minidoracat/humanitz-bot/blob/main/src/humanitz_bot/rcon_client.py>

The client documents fixed response ID 0, authentication type 0 followed by type 2, and no response to an empty command. LanGame uses a dedicated `humanitz_rcon` transport. The info response requires the explicit count, all documented header fields, the Players section, and exactly that many display-name lines after reading a complete length-prefixed RCON frame with both NUL terminators. Zero requires the full header, explicit zero, and an empty Players section or the native `No players connected` marker. Unknown, malformed, short, oversized, or timed-out replies are errors.

The live nonzero response arrived in one ID 0/type 0 frame with valid UTF-8, CRLF separators and no newline after the final player name. Authentication used ID 1/type 0 followed by ID 1/type 2. No additional response frame arrived during the existing 12-second budget. Requiring a trailing newline incorrectly rejected this complete native response. The adapter now uses the validated frame boundary plus the declared count, not EOF or an idle timeout, to complete it. Tests fragment TCP reads into three-byte pieces, including inside Unicode characters, while retaining complete RCON frames.

This is a HumanitZ-specific completion rule, not a generic Source RCON guarantee. Large native rosters spanning logical RCON frames have not been observed. The previous synthetic test that split the final name across two logical frames assumed a completion signal the native protocol does not provide: a complete-frame name prefix cannot be distinguished from a shorter complete name. Count-incomplete frames can still accumulate, but arbitrary splitting of the final name across logical frames is not claimed.

`info` supplies display names without account IDs. It remains the readiness probe. Live collection uses the same authenticated connection to read info, then (only for a nonzero count) Players. The observed Players reply is one ID 0/type 0 frame: leading CRLF followed by `Name (Steam64_+_|ProductUserId) Lv:0 Clan:None DPassed:0`, with no final newline or subsequent response. The complete frame and exact info count establish the capture boundary. Each row must contain its complete native identity and suffix fields; repeated identities, malformed rows, and count mismatches fail closed. Count-incomplete frames with complete rows can accumulate, but arbitrary splitting of individual rows across logical frames and large native rosters have not been observed. TCP fragmentation is covered separately by three-byte reads.

The transport returns an internal JSON object containing the two raw responses to the codec. Zero is represented by the verified zero info response and an empty Players string without sending Players. A timeout is never an empty result. Identities and kick targets come directly from each Players row, not from matching info names, historical logs, or partial Steam/EOS IDs. Duplicate names with distinct IDs remain distinct; only declared kick bindings are published. The runtime and persistent ban dispatch now use native response IDs without an empty-command marker. A response receipt is not verification of a kick/ban side effect, and unconfirmed commands are not retried. Live disruptive commands were not used to test this change.

The installed dedicated package examined during implementation was Steam build 23914958. Its native RCON sender enqueues response data, but the encrypted packaged command implementation does not establish a stronger response completion boundary. No player saves or roster data were inspected.
