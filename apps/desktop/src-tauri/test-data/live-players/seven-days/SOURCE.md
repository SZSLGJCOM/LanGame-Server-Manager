# 7 Days to Die listplayers response contract

The normal and empty fixtures are synthetic and contain no captured player data.

On 2026-09-27 the installed dedicated-server distribution's `7DaysToDieServer_Data/Managed/Assembly-CSharp.dll`, Steam build **24994542**, was inspected read-only with `System.Reflection.Metadata.PEReader`. The assembly was never loaded or executed. SHA-256: `7599FF7E972E8247E58A3830CD07A99EACDB66D889E63A39027DBF1F781B01E0`. No settings, saves or player data were inspected, and no commands were sent to a running server.

`ConsoleCmdListPlayers.Execute` emits a zero-based row sequence with this field order:

```text
0. id=<entity ID>, <name>, pos=(x, y, z), rot=(x, y, z), remote=True, health=<int>, deaths=<int>, zombies=<int>, players=<int>, score=<int>, level=<int>, pltfmid=<platform account>, crossid=<cross-platform account>, ip=<address>, ping=<int>
Total of N in the game
```

`Extensions.ToCultureInvariantString(Vector3)` supplies parenthesized comma-separated coordinates. Account values use `PlatformUserIdentifierAbs.CombinedString`, for example `Steam_76561190000000001` or `EOS_00000000000000000000000000000001`. Missing account/address values are `<unknown>`; network `GetIP` implementations may also return an empty string during disconnection. `pingToServer` is an `Int32`; negative telemetry is exposed as unknown ping. The collector consumes fixed fields from the end so a name containing commas or field-like text cannot shift the account. It requires every field, the matching count and contiguous indices, and does not project network addresses or coordinates.

`ClientInfo.InternalId` returns `CrossplatformId ?? PlatformId`. The collector projects only this account as a stable roster identity, with a pure platform ID value and matching `eos_id` / `steam_id` kind. The alternate platform account is display metadata. Entity IDs are non-stable session metadata and never command targets. Native `UserIdentifierSteam` requires 17 decimal digits; `UserIdentifierEos` validates 8–32 hexadecimal characters. Its string constructor stores the accepted value unchanged, and `CreateCombinedString(string)` only prepends `EOS_`; it does not pad short IDs to 32 characters. Unknown namespaces remain read-only, including when a supported secondary platform account exists; an unsupported internal account must not silently become another identity.

`ConsoleCmdKick.Execute` and `ConsoleCmdBan.ExecuteAdd` use `ConsoleHelper.ParseParamPartialNameOrId`, then `ClientInfoCollection.GetForNameOrId` / `ForUserId`, which accept combined platform account IDs and match either platform or cross-platform identity. The collector binds declared kick/ban actions to the canonical **combined** account ID, never to the entity slot or name. The ban command remains the module's explicit ten-year ban. `ConsoleCmdBan.ExecuteRemove` directly parses a combined platform account ID and is a blacklist operation, not an online-row action.

`AdminBlacklist.AddBan` updates the native blacklist and calls `AdminTools.Save`; it also removes an active banned account from native admin users. Steam Family Sharing may add a separate owner ban. `RemoveBan` saves when an entry existed, while its command prints a removal message even when none existed. `AdminTools.Save` logs and swallows write errors, so command output alone does not prove disk persistence. `BannedUser.ToXml` writes `platform`, `userid`, optional `name`, `unbandate` and `reason`; the native unban date includes time (`yyyy-MM-dd HH:mm:ss`). These native side effects must not be inferred as an automatic update to the application's settings.

These synthetic fixtures verify the parser and binding contract against static native code evidence. They are not a recorded live-server session or live kick/ban acceptance test.

The same IL inspection verifies the exact command output: `{account} banned until {local expiry}, reason: {reason}.`, followed, when applicable, by `Steam Family Sharing license owner {account} banned until {local expiry}, reason: {reason}.`. `PlatformUserIdentifierAbs.ToString` returns `CombinedString`. Names are not included in either confirmation line. The desktop collector accepts only complete lines for the authorized target followed by at most one distinct Steam owner, with the module's fixed `LanGame` reason and the same expiry. It rejects duplicated, malformed or reordered receipts, while allowing recognized timestamped native log lines inside the completed response. It then compares every named account's expiry and reason against native XML before one managed-settings write. This avoids importing an old ban after a native save failure, and preserves the explicitly confirmed family-owner ban through future materialization.

`TelnetConnection.submitInput` sends commands to `SdtdConsole.ExecuteAsync`, which appends them to a locked FIFO. `SdtdConsole.Update` executes index zero, sends its complete output list and only then removes it. For an unknown command, `executeCommand` emits exactly `*** ERROR: unknown command '<command>'` without running a handler. The dedicated ban transport therefore uses random, per-request unknown commands as beginning and ending completion markers on the same connection. It waits for exact complete marker lines, not socket silence, and returns only the enclosed response. Authentication, both markers and the ban share the existing eight-second transport budget; missing or malformed completion fails without resending the ban. Synthetic loopback TCP tests cover a family-owner line delayed past the idle timeout, interleaved disconnect logs, fragmented markers and missing completion. This specialized transport is selected only for the authorized Seven Days `ban_player` action; other Telnet operations keep their existing transport.
